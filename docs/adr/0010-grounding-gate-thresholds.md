# ADR 0010: グラウンディングゲートの閾値を実測分布に基づき grounding 0.6 へ引き下げる

- 状態: 採用（2026-08-03 実測、同日ガードレール version 2 として適用）→ **前提を撤回**（[ADR 0018](0018-retire-grounding-gate-as-quality-judge.md)。ゲートを品質判定から外したため閾値調整の意味が失われた）
- **通過率の定義について（2026-08-09, issue #143）**: ADR 0018 決定5は「ADR 0010 / 0015 / 0016 が記録している通過率は grounding 軸だけの数字」としたが、**本ADRについてはこれが当たらない**。本ADRの数字は grounding と relevance の AND 判定（`status=passed` 相当）である。詳細は下記「通過率の定義」を参照
- 関連: [ADR 0007](0007-observability-stack.md)（Guardrailsゲートの設計）、[ADR 0009](0009-openrouter-default-provider.md)（OpenRouter既定化。残課題として issue #63 を切り出した）、issue #63（本ADRの意思決定元）、[PR #72](https://github.com/yuyumama/AWS-MON/pull/72)（ゲート入力整形と計測基盤）

## 背景

ADR 0009 の本番検証で、無料 nemotron モデルのグラウンディングスコアが閾値付近（0.63〜0.73）で揺らぎ、初回ブロック→リトライで無料枠を余分に消費することが分かっていた（issue #63）。

PR #72 でゲート入力の整形（`grounding_source` を `read_documentation` の結果に限定、`guard_content` から「正解: A, D」ラベル行を除去、`correct_reason` に英語原文引用を促すプロンプト）と計測基盤を実装したうえで、**閾値を実測分布に基づいて再設定する**ことが本ADRの対象である。

それまでの閾値 grounding 0.7 / relevance 0.5 は `create_guardrail.py` の初期値であり、実測に基づいたものではなかった。

## 計測（2026-08-03, n=30）

`scripts/sample_gate_scores.py` で初回試行のスコア分布を採取した。

| 項目 | 値 |
|---|---|
| サンプル数 | 30（`--cert aip`、ドメインは重み付き抽選） |
| ゲート設定 | `AGENT_GUARDRAIL_ENFORCE=0`（レポートのみ）/ `AGENT_GUARDRAIL_RETRIES=0` |
| モデル | OpenRouter `nvidia/nemotron-3-ultra-550b-a55b:free` |
| 所要 | 合計73分、平均146秒/件、エラー0件 |

`AGENT_GUARDRAIL_RETRIES=0` としたのは、issue #63 の論点が**初回通過率**であり、既定の1のままでは記録されるのが再生成後のスコアになるため（`agent.py` のリトライループは `AGENT_GUARDRAIL_ENFORCE` の値に関係なく回る）。

### 通過率の定義（2026-08-09 追記, issue #143）

**本ADRの通過率はすべて grounding と relevance の AND 判定であり、ゲートの `status=passed` と同じ意味である。**
上表の見出しどおり relevance は 0.5 固定で、relevance 失格の2件（grounding 0.91 / 0.86）は
どの grounding 閾値でも落ちる。上の分布から再計算すると各行が一致する。

| grounding閾値 | grounding単軸 | AND（本表の値） |
|---|---:|---:|
| 0.7 | 60.9% (14) | 52.2% (12) |
| 0.65 | 60.9% (14) | 52.2% (12) |
| **0.6** | **69.6% (16)** | **60.9% (14)** |
| 0.55 | 78.3% (18) | 69.6% (16) |
| 0.5 | 87.0% (20) | 78.3% (18) |

[ADR 0015](0015-display-and-grounding-data-separation.md) / [ADR 0016](0016-generation-model-selection.md) の
計測表が grounding 単軸だったのに対し、本ADRは AND であるため、**この3つのADRの数字を横に並べて
比較してはいけない**（ADR 0016 の「60.9% → 82.1%」がその誤りである）。

**生データから `status` で再集計しても本表の 60.9% は再現しない。**採取時のガードレールは
version 1（grounding 0.7）で動いており、記録された `status` は閾値 0.7 の合否だからである
（`status=passed` は 52.2%）。60.9% は「閾値を 0.6 にしたら何件通るか」を分布から計算した
**反実仮想の値**であって、その時点で観測された合否ではない。ADR 0018 が出所を特定できないとした
「ADR 0010 の 60.9%（23件中14件）」はこの値である。

### 1. grounding 閾値を 0.7 → 0.6 とする

分布の空白帯（0.61〜0.73）の直下を切る位置であり、閾値の選択に恣意性が入りにくい。初回通過率は 52.2% → 60.9%。

**0.65 への引き下げは採らない。** この区間にサンプルが1件も存在せず、従来の 0.7 と結果が完全に一致するため、変更する意味がない。この点は、分布を採取する前には分からなかった判断材料である。

### 2. relevance 閾値は 0.5 のまま据え置く

23件中の relevance 失格は2件のみで、いずれも grounding は高い:

- grounding 0.91 / relevance 0.24
- grounding 0.86 / relevance 0.47

「根拠はあるが設問と整合していない」ケースを正しく捕捉できており、再設定の必要がない。0.4 へ下げると後者が通過してしまい、検出力を落とす割に得られるのは通過率 +1件にとどまる。

### 3. 適用はガードレールの新バージョン発行で行う（2026-08-03 実施済み）

DRAFT を直接書き換えると本番の判定が即座に変わり、切り戻し先が残らない。そのため**旧しきい値のスナップショットを先に発行**してから DRAFT を更新した。

| version | grounding | relevance | 位置づけ |
|---|---|---|---|
| 1 | 0.7 | 0.5 | 変更前のスナップショット（切り戻し先） |
| **2** | **0.6** | 0.5 | 本ADRの決定。prod の既定 |
| DRAFT | 0.6 | 0.5 | 次の変更の作業領域。運用では参照しない |

適用の内訳:

- `scripts/create_guardrail.py` に `--update` / `--publish` を追加し、既定しきい値を 0.6 に変更した（従来は同名ガードレールがあると更新経路がなくコンソール作業になっていた）。
- prod は Terraform 変数 `agent_guardrail_version`（既定 `2`）を AgentCore Runtime の `AGENT_GUARDRAIL_VERSION` に注入する。**切り戻しはこの変数を `1` に戻して apply するだけ**で、ガードレール側の操作は不要。
- ガードレールのIAM許可はバージョンを含まない ARN（`guardrail/{id}`）単位のため、版の切り替えで権限変更は生じない。

## 却下した代替案

- **grounding 0.55 まで下げる（issue #63 の目安の下限）**: 初回通過率 69.6% と効果は大きいが、追加で拾う 0.56 / 0.58 は低群 `[0.24 0.46 0.49 0.52 0.52 0.56 0.58 0.61 0.61]` の中央付近にあり、誤検出の救済ではなく品質の低い問題を通している可能性が高い。まず 0.6 で運用し、実測を見てから再検討する。
- **relevance も併せて 0.4 へ下げる**: 上記のとおり検出力の低下に見合わない。
- **閾値を変えず `AGENT_GUARDRAIL_RETRIES` を増やす**: リトライ1回あたり `structured_output` 1リクエストを消費する（ADR 0009 決定4-A で調査再実行は回避済み）。通過率を上げる手段としては閾値調整より高コストで、根本の校正ずれを放置する。

## 影響 / 留意

- 閾値を緩めるため、**ゲートを通過する問題の品質下限は下がる**。今回追加で通るのは grounding 0.61 の2件のみであり、影響は限定的である。品質の追認手段だった AgentCore Evaluations（Correctness）は [ADR 0011](0011-retire-online-evaluations.md) で廃止したため、**通過した問題の品質は目視確認でしか追えない**点に留意する。
- 本ADRの数値は**再生成なし（`RETRIES=0`）の初回試行**のもの。本番既定（`RETRIES=1`）での最終通過率はこれより高くなる。
- **適用後の効果測定は再サンプリングを行わず、prod の `grounding_gate` メトリクス（`status` / `attempt` 別）の蓄積で追う。** 分布は既知で初回通過率は 60.9% と予測できるため、73分／30件のバッチを再実行する費用対効果が低い。
- **スコア分布だけでは「ゲートが厳しすぎる」のか「生成が実際に弱い」のかを区別できない。** 0.6 を選んだ根拠は分布の空白帯という構造的特徴であって、低スコア帯の問題が実際に低品質だと確認したわけではない。閾値をさらに下げる判断をする際は、問題文の目視確認を伴うべき。

## 判明した別課題（本ADRの対象外）

- **not_run 23%（7/30）**: 本番の約4分の1の生成が品質ゲートを通っていないことになり、**閾値調整より影響が大きい可能性がある**（閾値 0.7→0.6 で稼げるのが23件中2件に対し、こちらは30件中7件）。issue #77 として切り出した。
  - **訂正（2026-08-03, issue #77 のログ解析による）**: 当初ここに「調査ターンで `read_documentation` が呼ばれず early return するケース」と記載していたが、実測ではそれは7件中1件のみだった。支配的原因（6件）は**調査ターンのモデル呼び出しが上流エラー（ストリーム途中の `openai.APIError`、`status_code` なし）で中断し、`DocsResearchError` としてドキュメントなし生成へフォールバック**したもの。MCP通信障害は確認されていない。詳細と対応は issue #77 を参照。
- **`sample_gate_scores.py` が `.env` を読んでいなかった**: `cli.py` / `server.py` と異なり `load_dotenv()` を呼んでおらず、そのままでは `AGENT_GUARDRAIL_ID` / `OPENROUTER_API_KEY` 未設定で全件 `not_run` になる。計測前に修正した。
- **`reasoningContent is not supported in multi-turn conversations with the Chat Completions API.`** の警告が多発する（生成自体は成功）。OpenRouter 経路のマルチターン会話で reasoning フィールドが欠落している旨で、別途確認の価値がある。
- OpenRouter 無料枠は 50 リクエスト/日ではなく **1000 リクエスト/日**だった（$10クレジット購入済みのため。`GET /api/v1/key` の `is_free_tier: false` で確認）。issue #63 が前提としていた「50/日」の制約は現状には当てはまらず、30件規模の採取は枠的に問題ない。
