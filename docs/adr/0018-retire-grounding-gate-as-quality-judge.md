# ADR 0018: グラウンディングゲートを品質判定から外し、決定的チェックと自己整合ジャッジに置き換える

- 状態: 採用（2026-08-09）。ADR 0007 の決定2、ADR 0010、ADR 0015 の前提を撤回・置換する。実装は段階的（本ADRの「移行手順」参照）
- 関連: [ADR 0007](0007-observability-stack.md)（決定2＝Guardrailsインラインゲート。本ADRの撤回対象）、[ADR 0010](0010-grounding-gate-thresholds.md)（閾値の実測設定）、[ADR 0011](0011-retire-online-evaluations.md)（品質担保をゲートに一本化した決定）、[ADR 0015](0015-display-and-grounding-data-separation.md)（表示用と評価用の分離）、[ADR 0016](0016-generation-model-selection.md)（本ADRで通過率の定義を訂正）、[ADR 0017](0017-test-strategy.md)（テスト先行）

## 背景

prod の問題バンク（`aws-mon-prod-questions`、aip 7問）を引用元AWSドキュメントと突き合わせて精査したところ、3問に実害があった。

| 問題 | gate score | 実害 |
|---|---:|---|
| `q_msjw3j7l_00eea781` | **0.92** | 技術用語が全てカタカナ転写され読めない。OpenSearch Serverless と Managed Clusters の取り違えもある |
| `q_msjvxu5d_92400f20` | 0.78 | 正解が `bedrock:GuardrailIdentifier` 条件キーとするが、正しくは `bedrock:ApplyGuardrail` アクション |
| `q_msjzxso6_2637d627` | 0.74 | 設問の要件3（逐次表示を損なわない）と正解（同期モード）が矛盾 |

**最高スコアの問題が最悪だった。**品質評価順と gate score の順位相関は ρ = −0.321（n=7、exact two-sided p = 0.498）で、正の信号が無い。

原因を追うと構造的な問題だった。`_gate_guard_content()` が採点するのは「正解の選択肢本文 + `grounding_claim_en`」であり、`grounding_claim_en` は ADR 0015 が作った**評価専用の内部フィールド**で `/generate` 応答からも除外され、利用者に届かない。**ゲートは製品ではなく「ゲート用に書かれた英訳」を採点している。**さらに `grounding_source` が英語原文であるため、ゲートを日本語の製品へ向け直すことが原理的にできない（ADR 0015 が実測で否定済み。日英分離で 65.5% → 82.1%）。

推測で変更せず、**問題本文と根拠原文を保存したうえで**再計測した。従来の `sample_gate_scores.py` は status/score/duration しか保存しておらず、ADR 0010/0015/0016 の全計測で「低スコアの問題が本当に悪かったか」を後から検証できなかった。

## 計測（2026-08-09、n=30 × 2腕）

| 腕 | guard_content | RETRIES |
|---|---|---:|
| arm1-mixed | 正解選択肢(日本語) + `grounding_claim_en`(英語) | 1 |
| arm2-claim-only | `grounding_claim_en` のみ | 0 |

モデル `nvidia/nemotron-3-ultra-550b-a55b:free`、判定 grounding 0.6 / relevance 0.5（ガードレール v2 の実設定）。

| | arm1 | arm2 |
|---|---:|---:|
| scored | 24 | 29 |
| 通過率 (status=passed) | 54.2% | 51.7% |
| grounding 中央値 | 0.73 | 0.80 |
| relevance 中央値 | 0.73 | 0.65 |
| 失敗内訳 (g のみ / rel のみ / 両方) | 4 / 6 / 1 | 2 / 8 / 4 |

### 1. ゲートは本物の欠陥を捕まえていない

機械的に検出できる欠陥（問いが無い / カタカナ退化 / ラベル重複 / URLエンコード混入 / 要件欠落）を正解ラベルとして精度を測った。

| 区分 | 件数 | うち欠陥あり | 精度 |
|---|---:|---:|---:|
| grounding のみで落ちた | 6 | 0 | **0%** |
| relevance のみで落ちた | 14 | 3 | 21% |
| 両方で落ちた | 5 | 2 | 40% |
| 通過した | 28 | 3 | （見逃し 11%） |

**grounding 軸の真陽性はゼロ。**relevance の真陽性3件はいずれも決定的チェックで無料かつ確実に拾える種類だった。加えて、上表の事実誤り2問（0.78 / 0.92）はゲートを通過している。**構造欠陥にも事実誤りにも効いていない。**

### 2. 低スコアの正体は良問だった

grounding < 0.6 の5件を取得原文と突き合わせた結果、5件中4件で原文はテーマと完全一致していた。grounding 0.05 の問題ですら、使用概念7つ中6つが原文に文字列として実在した。

低スコアの原因は**正解がシナリオ固有の具体的な設定値**（max tokens 1500、buffer size 1、threshold 95 等）であること。これらは当然ドキュメントに載っていない。**grounding は「ドキュメント知識をシナリオに適用した答え」を構造的に減点する。**満点は原文の丸写しであり、良い誤答は誤りである以上ドキュメントに存在しないので低スコアが正しい振る舞いになる。難易度と逆相関する指標である。

### 3. 再生成が良問を壊し、壊れた版を通していた

再生成11回のうち通過は3回。**そのうち2回は「問いが消えた回答不能な問題」だった。**

```
[4] 0.47 → 0.68 passed  設問 377→141字 (-63%)  問い欠落
[5] 0.65 → 0.85 passed  設問 233→124字 (-47%)  問い欠落
[9] 0.49 → 0.70 passed  設問 469→485字 (+3%)   正常
```

無傷で通過したのは11回中1回のみ。書き換わった箇所は設問 10/11、選択肢 9/11、`grounding_claim_en` 11/11。`grounding_claim_en` だけ書き換わった2件のスコア上昇は +0.09 / +0.04 と小さく、大きな上昇（+0.23、+0.92、+0.21、+0.20）はすべて全面書き直しを伴っていた。**スコア回復は設問を壊すことで得られていた。**

原因は `QUIZ_REGENERATE_FEEDBACK_PROMPT` の「原文に根拠のない主張は削って、問題と解説を作り直してください」。シナリオ（状況設定・要件・症状）こそドキュメントに無い部分なので、そこが最も削られる。

補助的な傍証（いずれも n が小さく単独では決定的でない）:

- 設問が途中で切れる割合: 初回 2/24 (8%) → 再生成後 3/11 (27%)
- grounding 変化と設問長変化の相関 ρ = −0.455（n=11、p = 0.16 で**有意ではない**）
- `content_invalid`: RETRIES=0 の9ラン全てで 0〜1件 に対し、RETRIES=1 の arm1 のみ 5件

### 4. guard_content の組み替えでは解決しない

日本語を除くと grounding は上がる（0.73 → 0.80）が relevance が下がる（0.73 → 0.65）。通過率は 54.2% → 51.7% で**有意差なし**（Fisher 正確検定 両側 p = 1.000）。grounding は英語原文と、relevance は日本語設問と照合するため、guard_content に求められる言語が逆方向である。

### 5. relevance は用途外

`guardrails-contextual-grounding-check.html` は対応用途を明示している。

> The supported use cases include summarization, paraphrasing, and question answering as defined in computer science discipline. (Conversational QA / Chatbot use cases are not supported.)

問題生成はこの3つのどれでもない。`query` は「受験者に出す設問」、`content to guard` は「正解の選択肢」であり、フィルタが想定する「利用者の質問」と「その回答」から役割が1段ずれている。閾値の問題ではなく用途の問題である。

## 決定

### 1. Guardrails グラウンディングゲートを品質判定から外す

スコアによる生成のブロックと、ブロック起因の再生成をやめる。**`research_incomplete`（調査ターンがドキュメントを取得できなかった）の fail-closed は維持する**（issue #77 の決定。調査が失敗したまま生成すると本当に根拠のない問題ができる）。現在 `agent.py` で `gate_enforced()` がこの2用途を兼ねているため、分離が必要である。

#### スコアの扱い: **案A（`ApplyGuardrail` 呼び出しごと撤去）を採る**（2026-08-09, issue #141）

| 案 | 内容 | 採否 |
|---|---|---|
| **A** | **`ApplyGuardrail` 呼び出しごと撤去** | **採用** |
| B | 呼び出しは残しスコアだけ記録 | 却下 |
| C | 呼び出しを残しジャッジの入力にする | 却下 |

根拠:

- **grounding 軸の真陽性はゼロである。**記録を続けても品質の信号にならない。Bはゼロ情報に文字数課金を払い続ける案になる
- **スコアは難易度と逆相関する。**「ドキュメント知識をシナリオに適用した答え」を構造的に減点するため、残すと将来また品質指標として誤用される。ADR 0016 の「初回通過率」（issue #143）が、まさに指標の意味を取り違えたまま採用根拠になった前例である
- Cは較正セットの拡張（「スコアは低いが正当」というケースの追加）が前提になる。ジャッジ自体がまだ実トラフィックで未検証（report-only 段階）であり、未検証の判定器に未検証の入力を足す順序は取らない

**Guardrails リソース自体は削除しない。**Terraform の環境変数注入と `bedrock:ApplyGuardrail` の IAM 許可は削除するが、ガードレール（SSM `/app/aws-mon/prod/agent-guardrail-id`）と `scripts/create_guardrail.py` は残す。方針が変われば変数と env の再追加だけで戻せる。

`quality.inlineGate` / `quality.evaluator` / `quality.score` / `quality.issues` の型は `packages/shared` に残す（既存 DynamoDB アイテムに値があるため。ADR 0011 の前例に倣う）。新規保存では `inlineGate` は常に `not_run` で、`score` / `issues` は付かない。

### 2. 品質担保を2層に置き換える

| 層 | 対象 | 手段 |
|---|---|---|
| 決定的チェック | 構造欠陥（回答不能・読めない・ラベル重複・URLエンコード混入） | `quiz_agent/quality_checks.py`。LLM呼び出しなし |
| 自己整合ジャッジ | 論理欠陥（設問要件と正解の矛盾、選択肢の固有名を解説が裏付けない、正解の一意性、正解ラベルと解説の食い違い） | OpenRouter 無料モデル。日本語の出荷物をそのまま読む |

ジャッジは**判定理由を返す**。これにより「設問から要件が欠落しています。要件と問いかけを補ってください」のような**欠陥特定型の再生成**が可能になる。現在のゲートはスコアしか返さないため正しい修復指示が書けなかった。

較正は**ミューテーション**で行う（良問を意図的に壊して負例を作る）。較正セットは `apps/agent/tests/fixtures/judge_calibration.json`（clean 3 + defective 9、4欠陥型を各2件以上）。

### 3. 調査(MCP)は主要な品質機構として維持する

計測で、取得原文は5件中4件でテーマと完全一致していた。露骨な捏造が少ないのはゲートのおかげではなく、**読んでから書いているから**である。

### 4. 事実誤りは無料の範囲では捕まえない

事実誤り（上表の `bedrock:GuardrailIdentifier`、Serverless/Managed 取り違え）を捕まえるには判定器に英語の原文を読ませる必要があり、[ADR 0011](0011-retire-online-evaluations.md) が費用で廃止した経路の再来になる。無料モデルに大量の英語原文を読ませても精度は期待できない。**残ることを受け入れる。**グラウンディングゲートを残しても捕まっていなかった（0.78 / 0.92 で通過）ため、本ADRの決定によって失うものではない。

### 5. ADR 0015 / 0016 の「初回通過率」の定義を訂正する

> **範囲の訂正（2026-08-09, issue #143）**: 当初この決定は対象を「ADR 0010 / 0015 / 0016」と書いていたが、
> **ADR 0010 は誤っていなかった**。ADR 0010 の閾値表は grounding と relevance の AND 判定であり
> （ADR 0010 本文が「grounding・relevance の AND 判定、relevance は 0.5 固定」と明記している）、
> 同ADRが記録した grounding 分布から再計算すると5行すべてが AND 判定の値と一致する。
> 訂正が必要なのは **ADR 0015 と ADR 0016** である。

ADR 0015 / 0016 が記録した通過率は **grounding 軸だけ**の数字である。ゲートは grounding と relevance の AND 判定であり、実際の通過率はより低い。過去ランを再集計すると ADR 0016 の表の5つの数字が `grounding >= 0.6` で完全に再現する。

混入の原因は `apps/agent/scripts/sample_gate_scores.py` の `summarize()` にある。`threshold_pass_rates` は grounding と relevance を**軸ごとに独立して**集計しており、AND を取った値を出していなかった。ADR 0015 / 0016 はこの出力の `threshold_pass_rates["0.6"]["grounding"]` をそのまま「初回通過率」として転記している。同スクリプトに `status=passed` ベースの集計を追加し、**今後の計測ではそちらを正とする**（issue #143）。

| ラン | ADR 0016 記載 | status=passed（実際） |
|---|---:|---:|
| m81-baseline-nemotron | 63.3% | 60.0% |
| **m81-ling3-after86** | **82.1%** | **67.9%** |
| m81-ling3-flash-free | 65.5% | 62.1% |
| m81-qwen3-30b-paid | 24.1% | 20.7% |
| m86-after-nemotron | 69.0% | 65.5% |

**ADR 0016 の採用根拠1「初回通過率が目安の80%に到達した（82.1%）」は成立しない。**実際は 67.9%。ただし**モデル選定の結論は変わらない**。両指標で ling-3.0-flash が全アーム中最良であり順位は保存されている。誤っているのは達成判定であって選定ではない。

**追記（2026-08-09, issue #143）**: 順位は保存されるが**差は縮む**。単軸では1位 82.1% と2位 69.0% で 13.1 ポイント離れていたのに対し、`status=passed` では 67.9% と 65.5% で 2.4 ポイント（n=28 / n=29）しかない。通過率だけを根拠にモデルを選べる差ではないため、ADR 0016 の実質の選定根拠は所要時間（中央値 146s → 54s）である旨を同ADRに追記した。

**ADR 0016 が背景で引用する「ADR 0010 の 60.9%（23件中14件）」の出所も特定した。**これは ADR 0010 が閾値 0.6 を採用したときの AND 判定の通過率であり、同ADRが記録した grounding 分布（低群9件・高群14件）と relevance 失格2件から再計算すると一致する。生データを `status` で再集計しても再現しないのは、採取時のガードレールが version 1（grounding 0.7）で動いており、記録された `status` が閾値 0.7 の合否（52.2%）だからである。60.9% は「閾値を 0.6 にしたら何件通るか」という**反実仮想の計算値**であって観測値ではない。したがって ADR 0016 の背景表は、**AND 判定の 60.9% と単軸の 82.1% を並べていた**ことになる。

**issue #77 再サンプリングの 53.8%（26件中14件）は依然として出所を特定できていない。**該当日のファイルのどちらでも、単軸・AND のいずれで集計しても再現しなかった。

## 移行手順

ADR 0011 が「品質担保は Guardrails ゲートに一本化」と決めているため、**先にゲートを外すと品質機構が空白になる**。次の順序で進める。

1. 決定的チェックを生成パスに配線する（fail-closed）
2. 自己整合ジャッジを実装し、較正セットで無料モデルを選定する
3. グラウンディングゲートを撤去する（`gate_enforced()` の2用途分離を含む）
4. 調査プロンプトを2ページ・制約衝突型に変更する（難易度対策）

### 較正結果（2026-08-09、n=12 × 4候補）

`scripts/run_judge_calibration.py` の実測。採否基準は defective 9件中8件以上を検出し、
clean 3件の誤検出がゼロ、判定不能がゼロ。

| 候補 | 検出 | 型一致 | clean誤検出 | 判定不能 | 採否 |
|---|---:|---:|---:|---:|---|
| `google/gemma-4-26b-a4b-it:free` | 3/9 | 3/9 | 0/3 | 4 | 不可 |
| **`nvidia/nemotron-3-super-120b-a12b:free`** | **8/9** | **6/9** | **0/3** | **0** | **採用** |
| `openai/gpt-oss-20b:free` | 0/9 | 0/9 | 0/3 | 12 | 不可 |
| `nvidia/nemotron-nano-9b-v2:free` | 3/9 | 2/9 | 0/3 | 0 | 不可 |

**基準を満たしたのは1候補だけで、選定は消去法である。**偽陽性ゼロ優先・型一致率という
優先順位を使う場面が無かった。落選理由:

- `openai/gpt-oss-20b:free` は12件すべてが API エラー（`400 Provider returned error`）。
  ADR 0016 が `gpt-oss-120b` で観測した「構造化出力が返らない」が 20b 版でも再現した
- `google/gemma-4-26b-a4b-it:free` は4件が `No choices found in the response`
- `nvidia/nemotron-nano-9b-v2:free` はエラーこそ無いが検出 3/9

**留意**: 採用モデルは生成モデル（`nemotron-3-ultra-550b-a55b:free`）と ID は異なるが
同じ nemotron ファミリーである。ADR 0007 が削除した「同一モデルへの再質問」には当たらないが、
盲点が相関するリスクは残る。基準を満たす他候補が無いため選択の余地が無かった。
report-only で実トラフィックの分布を採る際にここを注視する。clean の誤検出は4候補すべて
ゼロだったが、較正セットの clean は3件しかないので確証にはならない。

### 難易度の効果測定（2026-08-09、n=30 × 変更前後）

第1〜3段を適用した状態で、`prompts.py` と `tool_limits.py` だけを #142 適用前に戻して比較した。

| 指標 | 変更前 | 変更後 |
|---|---:|---:|
| 成功 / エラー | 24 / 6 | 26 / 4 |
| 設問に登場する機能名の種類数（中央値） | 2.5 | **3.5** |
| 3種類以上を含む設問 | 12/24 = 50% | **21/26 = 81%** |
| 設問長（中央値） | 334字 | **404字** |
| `duration_sec` 中央値 / p90 / 最大 | 196s / 284s / 330s | 228s / 335s / **464s** |
| 取得原文（中央値） | 12,168字 | 10,415字 |

**難易度は上がったと言える。**本文を読んだ判定:

- 変更前は Guardrails 単独・PIIマスク単独のように**1機能の仕様確認**に収まる設問が多く、
  正解は該当ドキュメントの記述をほぼそのまま言い換えたものだった
- 変更後は「ハイブリッド検索 × 階層的チャンク × メタデータ上限」「Provisioned Throughput ×
  Cross-Region Inference × ティア上限」のように、**複数機能の制約を突き合わせないと
  正解に到達できない**設問が主になった。誤答も実在する機能の組み合わせで、
  「要件のどれを満たさないか」で誤りになる形になっている

`duration_sec` は伸びたが（中央値 196s → 228s、最大 330s → 464s）、
**ADR 0014 の job 締切 600s を超えた生成は両群ともゼロ**。`AGENT_DOCS_SEARCH_LIMIT` は
2 のままでよい。

**指標「誤答の否定理由が『ドキュメントにない』だけの割合」は使えなかった。**両群とも 0%
（誤答理由 0/75 と 0/79）である。この兆候は ADR 0018 の計測で**再生成後**の問題に現れたもので、
第3段で再生成そのものを撤去した結果、観測されなくなった。今後この指標は追わない。

計測スクリプトの名前も変えた。`scripts/sample_gate_scores.py` → **`scripts/sample_generations.py`**（ゲートのスコアではなく、生成された問題本文・調査完了状況・ジャッジ判定を採る）。EMFメトリクスも `GateEvaluationCount` / `GroundingScore` / `RelevanceScore` → **`ResearchCount`** に置き換えたので、ダッシュボードの差し替えが要る。

issue #143 で `summarize()` に足した `status=passed` ベースの集計は、ゲートと一緒に無くなった。**訂正の内容（過去の通過率は grounding 単軸だった）は ADR 0015 / 0016 の本文に残っている。**

### 決定的チェックの誤検出率（2026-08-09、実データ83設問）

`scripts/check_quality_defects.py` を prod 7問 + 計測データ + 較正セットに当てた。

| 検査 | 検出 | 誤検出 |
|---|---:|---:|
| `duplicate_option_labels` | 1 | 0 |
| `missing_question_prompt` | 7 | 0（**修正後**） |
| `url_encoded_text`（#139 で新設） | 1 | 0 |
| `katakana_degraded` | 0 | 0 |

新設した `url_encoded_text` の検出1件は真陽性で、設問に `%0A%0A` が生のまま混入していた実物である。

**ただし `missing_question_prompt` に誤検出が1件見つかり、判定条件を広げた。**

```
[arm2:31] 337字 ...「どのガードレール構成を選択し、どのように適用すれば要件をすべて満たせますか？」
```

問いかけを持つ正常な設問だが、旧パターン `どれか|どれですか|選んでください|選択してください`
が「〜ますか？」形を取りこぼしていた。この検査は #139 で fail-closed に配線済みのため、
放置すると正常な設問が再生成に回される。`でしょうか|ますか|選びなさい|選べ` を足して解決した
（真の欠落7件は疑問形を持たないため検出は落ちない。83設問で確認）。

**「n=N で決めた閾値は信用できない」が n=54 → 83 で再現した。**この判定条件は前回 54設問で
検証済みだったが、arm2 のデータを足した途端に誤検出が出た。**新しい判定条件を生成パスに
繋ぐ前に実データ全件へ当てる**という手順は、条件を変えるたびに繰り返す必要がある。

計測スクリプトのメタデータにも同種の欠陥があった。`sample_generations.py` が
`docs_search_limit` の既定値を文字列 `"1"` でハードコードしており、実装の既定
（`tool_limits.DEFAULT_SEARCH_LIMIT = 2`）と食い違っていた。生成自体は 2 で走っていたが、
**記録だけが計測条件を誤る**状態だった。定数を `tool_limits` から引くよう直した。

## トレードオフ / 留意

- **事実誤りが残る。**無料縛りの帰結であり、有料の判定器を許容する方針に変われば再検討の余地がある
- **ジャッジは未検証である。**較正セットは合成負例であり、実トラフィックでの精度は保証しない。ADR 0010 と同様、レポートのみモードで分布を採ってから強制に切り替えるのが安全
- **決定的チェックの閾値は n=7 では決められなかった。**当初の `katakana_degraded`（ASCII技術語を含まない選択肢が過半数）は prod 7問を完璧に分離したが、計測46問に当てると3件を誤検出した（プロンプトキャッシュのように外来語だけで自然に書ける題材）。判定軸を「カタカナ語のスペース区切り」に変更して54設問で誤検出ゼロを確認した。**今後の判定条件も、生成パスに繋ぐ前に実データ全件に当てて誤検出率を測ること**
- Guardrails リソース自体（`AGENT_GUARDRAIL_ID`）を削除するかは本ADRでは決めない。スコアをジャッジへの参考情報として渡す案が残っている

## 追記: 評価専用フィールドの撤去（2026-08-10、issue #149）

ゲート撤去の残置物レビューで、`explanation.grounding_claim_en` が**消費者ゼロのまま生成され続けている**ことが分かった。唯一の消費者は `ApplyGuardrail` に渡す claim であり、ゲートと同時に消えていた。にもかかわらず、

- `schema.py` は必須フィールドとして要求し続け
- `prompts.py` は毎生成・毎再生成で「英語で2〜4文書け」と指示し続け
- `server.py` は応答から除外して捨てていた

**書かせて、検証もせず、返す前に捨てる**状態だった。無料枠モデル運用では出力長がそのまま安定性とコストに効くため、[ADR 0015](0015-display-and-grounding-data-separation.md) の決定1〜4ごとフィールドを削除した。較正セット用に空文字を補っていた回避コード（`check_quality_defects.py` の `_with_claim`、`run_judge_calibration.py` の `setdefault`）も同時に消えた。

DynamoDB への影響は無い。ADR 0015 の決定で、このフィールドは元々保存していない。

**教訓**: 判定器を撤去するときは、判定器**だけ**でなく「その判定器のためだけに存在していた入力」も同時に消す。今回は撤去から1日、`guardrail.py` の削除（#141）から見て後追いで気づいた。

## 却下した代替案

- **閾値を再調整する**: grounding 軸の真陽性がゼロなので、どの閾値でも真陽性は増えない
- **`guard_content` を組み替える**: 計測4のとおり grounding と relevance が逆方向に動き、通過率は有意に変わらない
- **再生成プロンプトだけを直す**: 範囲限定は実施した（本PRに含む）が、ゲート自体の真陽性がゼロである以上、救う価値のある問題がほとんど無い
- **Langfuse 等の外部評価基盤へ移行する**: 今回見つかった欠陥はどの基盤でも自動検出されない。フェーズ3の検証テーマ（AIオブザーバビリティ）を壊す割に得るものが無い
