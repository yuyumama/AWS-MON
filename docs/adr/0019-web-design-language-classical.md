# ADR 0019: apps/web のデザイン言語を「読み物としての問題集」へ差し替え、スマホ対応を作り直す

- 状態: 採用（2026-08-14）。`AGENTS.md`「コード方針」と `apps/web/src/styles.css` 冒頭が宣言していたデザイン言語「青のノートと丸つけ」を置換する
- 関連: [ADR 0017](0017-test-strategy.md)（UI/UX はテスト対象外・UIロジックの置き場所）、`AGENTS.md`「コード方針」、issue #155（本ADRの作業中に発見した既存バグ。本ADRとは独立）

## 背景

`apps/web` のスマホ対応は部分的にしか入っていない。

- メディアクエリは `styles.css` の `@media (max-width: 560px)` 2ブロックだけ（`:878` と `:1469`）
- 対象は `.session-row` / `.masthead` / `.quiz-bar` / `.result-sheet` / `.generation-wait-head` / `.question-list-filters` 等に限られる
- **ログイン画面と復習リストには専用のSP対応が一切ない**

デザイン検討（Claude Design プロジェクト「レスポンシブデザイン方針の相談」）で、現UIの再現に加えて2案を作成した。

| 案 | ビジュアル言語 |
|---|---|
| 案A / Modernist | 角丸と影を捨て、2px罫線と余白の規律で構造を出す。ゴシック800 |
| 案B / Classical | 問題文と解説を「紙面」として扱う。ヘアライン罫線と余白。明朝 |

**両案のレスポンシブ構造は同一である**（スマホ = 上部追従バー＋下部固定アクションバー＋解説はボトムシート、PC = 中央1カラム維持）。差はビジュアル言語だけだった。

## 決定

### 1. 案B（Classical）を採用する

デザイン言語を次のように差し替える。

| | 旧（青のノートと丸つけ） | 新（読み物としての問題集） |
|---|---|---|
| 配色 | 青 `#2867a8` / ○ `#0e8570` / ✕ `#c4484f` | **継承（変更なし）** |
| 面の作り | 角丸（`--radius` 10px / 14px）と淡い影を全面に | ヘアライン罫線と余白。角丸は 2px / 4px まで落とす |
| 影 | `.sheet` / `.nav` など面に常用 | 常用をやめ、浮遊要素（ボトムシート・モーダル）だけに残す |
| 見出し | ゴシック太字 | 明朝（`Hiragino Mincho ProN` / `Yu Mincho` / `Noto Serif JP` / serif） |
| 本文の行長 | 制約なし | 約60文字で止める（`--measure: 60em`） |

行長の単位は `em` であって `ch` ではない。`ch` は「0」の字幅（≒0.5em）なので、`60ch` は全角30文字ぶんにしかならず、PCで本文だけが選択肢や罫線より内側で折り返す。全角1文字 = 1em で数えること。

配色を継承するのは、`styles.css` 冒頭が記録しているとおり accent/ok/ng が dataviz validator で検証済み（surface `#fafcfe`）であり、コントラストの再検証を避けられるため。

問題文と解説がこのアプリの主コンテンツであり、「読み物」として扱う方針は内容の性質と一致する。

### 2. スマホ対応を作り直す

- 上部にスクロール追従の細いバー
- 下部に固定アクションバー
- 解説はボトムシート
- PC は中央1カラムを維持し、同じ部品が幅だけ伸びる

**ブレークポイントは既存の 560px を単一で維持する。** 変更点を「中身」だけに限定でき、差分が読みやすい。560px 以下は実質スマホ専用なので、下部固定バーの対象としても妥当。

### 3. デザインモックは仕様ではなく版面の参考である

**機能・インタラクション・アクセシビリティは現行実装を正とする。** モックに描かれていない要素を「削除の指示」と見なさない。

この原則が必要な理由は実測に基づく。デザインプロジェクトの `github.md` は問題リスト・復習リスト・ログインの3画面を「参考のみ（未再現）」と記録しており、実際にモックと実装を突き合わせたところ7件の齟齬があった。

| 齟齬 | 実装側の根拠 |
|---|---|
| 一覧のタイトルに問題文の冒頭を使っていた | `QuestionListView.tsx` / `ReviewView.tsx` は `item.summary` を使う。`QuizItem.summary` のスキーマは「問題文の冒頭をそのまま切り出さないこと」と明記 |
| セッション行の「削除」ボタンが無い | `HomeView.tsx:143`（確認ダイアログ `:443` 付き） |
| ログインの初回パスワード変更画面が無い | `LoginView.tsx:54` `phase === "newPassword"` |
| 生成待ちの「検証」が永久に待機 | 実装側のバグ。issue #155 で別途対応 |
| 問題リストが遷移に見える | 現行は `aria-expanded` / `aria-controls` のアコーディオン |
| 出題モードが radio → セグメント | `HomeView.tsx:360-376` の `fieldset` + `legend` + `radio` |
| 資格/ドメインが native `select` → タップ行 | `HomeView.tsx:324,345`。native を捨てると iOS のホイールUIを失う |

うち1件目はモック側を修正済み。**残りはモックを採用せず、現行実装を維持する。**

### 4. モックに無い状態は案Bの語彙から導出する

モックが描いているのは正常系の1状態だけである。次はモックに存在しないが実装には必要で、罫線・明朝・余白・浅い角丸という規則から導出する。

- skeleton 17クラス（`skeleton-sheet` / `skeleton-quiz-bar` / `skeleton-session-list` / `skeleton-option` 他）
- エラー3種（`notice` / `notice-error` / `action-error`）
- 空状態3箇所、`review-missing`
- モーダルダイアログ（削除確認）。案Bはボトムシートの語彙は持つがモーダルの語彙を持たない
- PC版のホーム・ログイン・生成待ち

## 実装の順序

各画面が必要とする共通部品は次のとおり。ボトムシートを使うのは出題だけで、追従バーと下部固定はホームが初出になる。

| 画面 | 追従バー | 下部固定 | ボトムシート | 規模 |
|---|:-:|:-:|:-:|---|
| ログイン | – | – | – | 149行 |
| ホーム | ✓ | ✓ | – | 488行 |
| 問題リスト / 復習リスト | ✓ | – | – | 380 / 330行 |
| 生成待ち | – | ✓ | – | 110行 |
| 出題・解説 | ✓ | ✓ | ✓ | **929行** |

このため **小さい画面から着手し、929行の出題を最後に回す**。共通部品の語彙を小さい画面で枯らしてから最大の画面に適用する。

1. 基盤（本ADR + 宣言更新 + トークン/罫線/タイポ/余白）
2. ログイン
3. ホーム（追従バー・下部固定の初出）
4. 問題リスト・復習リスト（`review-list` / `review-item` 系を共有するため1本にまとめる）
5. 生成待ち
6. 出題・解説（ボトムシートの初出）

共通シェル部品は基盤に含めない。使われないCSSは実機で検証できないため、最初に必要とする画面と一緒に入れる。

## 検収

ADR 0017 のテスト方針表は UI/UX をテスト対象外としている。つまり**この作業には自動の回帰ネットが無い**。上表の齟齬7件は、いずれも「静かに落ちても誰も気づかない」クラスである。

そのため画面ごとに次を行う。

- **非退行の機械チェック**: 削除ボタン、`aria-expanded` / `aria-controls`、`fieldset` + `legend`、`aria-label`、`newPassword` フェーズが残っていることを確認する。委譲プロンプトの完了条件に埋め込む
- **CDP実測**: 390px / 820px のスクリーンショットを撮って版面を確認する
- **prod実機確認**: 検証環境が存在しない（`infra/envs` は local / prod のみ）ため、prod が唯一の実機である。1画面マージごとに prod へ出し、実機で確認してから次の画面に着手する

## 影響

- `AGENTS.md`「コード方針」の「既存の『青のノートと丸つけ』モチーフを維持」を本ADRの方針に差し替える
- `apps/web/src/styles.css` 冒頭のデザイン言語コメントを差し替える
- 段階マージのため、作業期間中は明朝化済みの画面と未対応の画面が混在する。ソロ運用であり、実機で早期に問題を見つける利益のほうが大きいと判断した

## 却下した案

- **案A（Modernist）**: レスポンシブ構造は案Bと同一で、差はビジュアル言語のみ。選択は好みの問題であり、案Bを採った
- **構造とビジュアルを分けて段階的に決める**: 構造だけ先に入れて見た目を後で選ぶこともできたが、2回に分けて全画面を触ることになり総コストが上回る
- **モックを実装に合わせて描き直してから着手**: 齟齬7件をデザイン側で修正してから実装に入る案。往復コストに見合わない。モックは版面の参考と位置づけ、実装を正とすることで解決する
