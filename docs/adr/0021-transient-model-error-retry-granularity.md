# ADR 0021: 一過性モデルエラーの再試行をモデル呼び出し単位にし、調査フェーズに実時間予算を設ける

- 状態: 採用（2026-08-29）
- 関連: [ADR 0012](0012-openrouter-only-inference.md)（OpenRouter一本化）、[ADR 0014](0014-generation-retry-policy.md)（job側のリトライ方針と10分締切）、[ADR 0016](0016-generation-model-selection.md)（生成モデルの選定）、issue #182（締切をAPIからagentへ渡す）

## 背景

2026-08-28、prod で問題生成が3連続で失敗した。ジョブに記録された失敗理由はいずれも
`agentcore request failed: aborted（ジョブ作成から10分の締切を超えるため、再試行を終了しました。）`
だったが、これは症状であって原因ではない。

### 真因: OpenRouter は HTTP 200 のボディにエラーを載せる

上流が過負荷のとき、OpenRouter は次を返す。

```
HTTP status = 200
body = <keep-alive の空白パディング>
       {"error": {"message": "Upstream error from Nvidia: Service temporarily overloaded",
                  "code": 502}}
```

`502` は**ボディの中の値**であって HTTP ステータスではない。ここから3つの帰結がある。

1. openai SDK 組み込みの `max_retries`（5xx を対象とする）は発火しない。HTTP としては成功しているため。
2. 例外は `status_code` を持たない `openai.APIError` として現れる。
3. strands 既定の `ModelRetryStrategy` は `ModelThrottledException`（429）以外を再試行しないため、この例外を握り潰し、調査ターン全体が落ちる。

つまり **HTTP レイヤでも strands 既定でも拾えない**失敗である。

### 増幅させていた構造: 再試行の粒度

`_researched_agent()` は調査失敗のたびに `Agent` を作り直していた。失敗した会話履歴を次の試行へ持ち越さないための意図的な設計だったが、一過性のモデルエラーに対しては過剰だった。

prod ログの実測値:

- 1回の調査ターン再構築に **約150秒**（2026-08-28 の失敗ジョブで 14:01:5x → 14:04:24 → 14:06:47 → 14:09:20）
- 捨てていた成功済みツール呼び出しは **最大8回**（`docs_research_failed` の `successful_tool_calls`）
- 単発のモデル呼び出しの失敗率は計測時点で **20〜50%**（自リポジトリからの実測。10回中2回、および6回中3回）

1回の調査ターンはツールユースで7回前後のモデル呼び出しを行う。単発20%でもターン内で1回以上失敗する確率は約79%、50%なら約99%になる。**ほぼ必ず踏む**失敗に対して、毎回150秒の作り直しで応じていたため、3試行で調査だけに450秒を費やし、[ADR 0014](0014-generation-retry-policy.md) の10分締切を超えていた。

### 締切超過の見え方

さらに、API 側が 600 秒で abort した後もエージェントは走り続けていた（14:27/14:28 に FAILED 確定したジョブの調査失敗ログが 14:33/14:38/14:40 に出ている）。このため利用者に見える文言が真因ではなく汎用の「aborted」になっていた。

## 決定

### 1. 一過性モデルエラーはモデル呼び出し単位で再試行する

strands の `_handle_model_execution` は例外種別を問わず `AfterModelCallEvent` を発火し、フックが `event.retry` を立てれば**同じ messages でモデル呼び出しをやり直す**（会話履歴は保たれ、失敗した応答だけが破棄される）。この拡張点を使う。

`quiz_agent/model_retry.py` に `TransientModelRetry`（`HookProvider`）を置き、調査 Agent に既定の `ModelRetryStrategy` と**併用**する。役割分担は次のとおり。

| フック | 対象 | 挙動 |
|---|---|---|
| `ModelRetryStrategy`（strands既定） | `ModelThrottledException`（429） | 従来どおり。枯渇後は `QuotaExhaustedError` |
| `TransientModelRetry`（本ADR） | `APIError` かつ `status_code` なし | 履歴を保ったまま同一呼び出しを再実行 |

429 を新フックが拾わないことは必須である。日次枠切れは待っても回復せず、フォールバックも再試行もしない既存経路（[ADR 0014](0014-generation-retry-policy.md) の `rate_limited`）を殺してはならない。

既定は初回を含めて4試行（再試行3回）、バックオフは 3秒 → 6秒 → 12秒で頭打ち。

### 2. 外側の調査ターン再構築を2回から1回に減らす

内側を足すだけでは総時間が伸びて締切超過が悪化する。150秒かかる作り直しを減らして付け替える。

| | 変更前 | 変更後 |
|---|---|---|
| モデル呼び出し単位（内側） | なし | 3回リトライ |
| 調査ターン再構築（外側） | 2回リトライ（計3試行） | 1回リトライ（計2試行） |

0 にはしない。内側で拾えない失敗（MCPサーバの異常、内側の枯渇）への保険が要る。単発失敗率50%の悪条件では内側3リトライでも約36%が枯渇するため、外側1回込みで約13%まで下げる。

### 3. 調査フェーズに実時間予算を設ける

内側リトライは1回が安いぶん、上流が恒常的に壊れているときは無限に粘って締切を食い潰す。回数とは独立に**実時間の上限**を設け、超えたら再試行を立てずに通常の失敗経路へ落とす。

既定は `AGENT_RESEARCH_BUDGET_SECONDS = 420`（7分）。根拠は成功時の実測分布である。

```
調査フェーズ所要時間（2026-08-14 prod、成功9件、秒）
133  135  146  152  166  182  269  306  368
```

中央値166秒に対して最大368秒。当初検討した300秒では9件中2件の成功実績を予算切れで落とすため採らない。420秒なら実測最大に対して余裕があり、生成（実測59秒）とジャッジ（実測23秒）を足しても10分締切に約100秒残る。

**予算は調査フェーズ全体で1つ**とし、外側の作り直しで巻き戻さない。Agent ごとに張り直すと外側2試行で最大840秒粘れてしまい、締切を超える。

同じ理由で、**予算を使い切った後は外側の作り直しも行わない**。内側が予算切れで諦めたあとに約150秒の作り直しを始めると、420秒を使い切ったうえさらに1ターン回すことになり、予算が「調査フェーズ全体の上限」として機能しなくなる。外側の作り直しが意味を持つのは、予算が残っている時点で起きた失敗（MCP異常など、開始直後に速く失敗するもの）に対してである。

### 4. 生成フェーズのバックオフを揃える

`structured_output` は `AfterModelCallEvent` を発火しない（strands の仕様）ため内側フックの対象外であり、`_structured_quiz_with_retries()` が唯一の再試行地点になる。ここは同一 Agent で再試行するため履歴の破棄は起きていないが、バックオフが 0.8秒 / 1.6秒 と短かった。上流混雑は数秒から数十秒持続するという既存の実測と整合しないため、調査フェーズと同じ 3秒 / 6秒 に揃える。

### 5. 内側の再試行回数を失敗ログに残す

`docs_research_failed` に `transient_retries`（内側の累計）と `budget_exhausted` を追加する。回数切れと予算切れは対処が異なる（前者は上流品質、後者は締切設計）ため、ログで区別できる必要がある。

## 却下した代替案

- **モデルを別の無料モデルに切り替えるだけで済ませる**: 即効性はあるが、別の無料モデルでも同じ性質の上流障害は起こりうる。粒度の問題を残したまま運に頼ることになる。切り替え自体は独立した打ち手として有効であり、本ADRはそれを否定しない。
- **openai SDK の `max_retries` に任せる**: OpenRouter が HTTP 200 を返す以上、SDK のリトライ条件に合致しない。動かない。
- **`ToolCallStructuredOutputModel` をラップしてモデル層で再試行する**: strands が `AfterModelCallEvent` という拡張点を用意しており、自前のラッパよりも会話履歴の扱いが正しい（失敗した応答だけを破棄する処理が本体側にある）。
- **外側の作り直しを0にする**: 内側で拾えない失敗に無防備になる。悪条件では内側だけで約36%が枯渇する。
- **実時間予算を設けない**: 上流が恒常的に壊れているとき、安価な内側リトライが締切まで粘り続ける。今回の障害の再現になる。
- **予算を300秒にする**: 成功実績（最大368秒）を切ってしまう。

## 影響 / 留意

- Terraform 変更は不要。新しい環境変数（`AGENT_RESEARCH_BUDGET_SECONDS` / `AGENT_TRANSIENT_RETRY_ATTEMPTS`）はすべて既定値で動く。デプロイはエージェントのコンテナ再ビルドと AgentCore Runtime の更新のみ。
- **`AGENT_RESEARCH_BUDGET_SECONDS`（420秒）は、`apps/api` の `jobDeadlineMs`（600秒）および worker の `AGENT_REQUEST_TIMEOUT_MS`（600000）と同期して保つ必要がある**。同じ「10分」が3か所に複製された状態であり、締切を変えるときは3か所すべてを直さなければ静かにズレる。この重複の解消は issue #182 で扱う（APIが締切そのものを invoke ペイロードで渡す）。
- 予算はあくまで当て推量である。ジョブがキューで待たされたりコンテナのコールドスタートに時間を食っていれば実際の残り時間は420秒より短いが、エージェントはそれを知らない。これも issue #182 の対象。
- 最悪の成功例は調査368秒 + 生成59秒 + ジャッジ23秒 = 450秒であり、10分締切に対する余裕は150秒しかない。**締切そのものの妥当性は別途見直す価値がある**。
- 本ADRは agent 内部の再試行粒度を扱う。job 側の失敗種別ごとのリトライ方針（[ADR 0014](0014-generation-retry-policy.md)）は変更しない。
